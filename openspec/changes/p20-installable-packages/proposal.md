## Why

The `heros` CLI is the platform's **free, offline, no-account** entry point — it runs discovery, the codemod,
and eval **in the user's own build environment with the user's own provider keys** (README §"Delivery
surfaces", [P11](../../../docs/prd/P11-cli-ci-integration.md)). P11 built the **supply-chain floor**:
[`scripts/release-cli.sh`](../../../scripts/release-cli.sh) builds one self-contained binary per native runner,
writes a sorted `SHA256SUMS`, and signs it with the ed25519 release key via
[`cmd/herossign`](../../../cmd/herossign/main.go); the verification is documented and tested
([`docs/release/cli-verification.md`](../../../docs/release/cli-verification.md), `TestReproducibleBuild`).

But nothing exists between "a binary can be built" and "a stranger on macOS, Ubuntu, or Windows installed it
and ran their first eval." There is **no release workflow at all** — `.github/workflows/` holds only `ci.yml`
and `heros-eval.yml`, so nothing on a tag builds the matrix, merges the per-runner artifacts into one signed
`SHA256SUMS`, and publishes a **GitHub Release**; a release today could only be assembled and uploaded **by
hand**, which the DevOps rulebook forbids ("物理上禁止任何人手工上传文件到 release"). There are **no install
channels** — no `curl … | sh` / PowerShell one-liner that detects OS/arch, **verifies checksum + signature
before placing the binary on `PATH`**, and no Homebrew tap, Scoop/winget manifest, `.deb`/`.rpm`, or container
image; so the only "install" is *download a raw binary, read a doc, run `shasum -c` by hand, `chmod +x`* — which
silently drops the signature step the CLI's threat model depends on ("runs inside your CI with access to your
repository, so a compromised release is a compromise of every build it runs in"). There is **no OS-trust
posture** — an unsigned Mach-O is **quarantined by Gatekeeper** and a downloaded `.exe` trips **SmartScreen**,
and there is no documented answer, so the honest first-run experience is an OS malware-shaped warning. There is
**no first-run onboarding** — nothing greets a fresh `heros` and walks it to a first success. And there is **no
self-update** — no `heros upgrade`, and therefore no *safe* one (the naïve versions auto-execute a download or
phone home on every command, breaking the security posture and the offline/no-account promise).

P20 closes all of it as **pipeline + installers + posture** — it adds no product feature and no statistic. It
is downstream of P11 (the binary + supply-chain floor) and P19 (the platform deploy the *linked* mode targets)
and changes **neither**: it wraps them in a distribution. Product rationale:
[`../../../docs/prd/P20-installable-packages.md`](../../../docs/prd/P20-installable-packages.md).

**Boundary with P19.** P19 delivers the **platform to a server/cluster** (Docker Compose, Kubernetes, air-
gapped) — the *fleet* delivery. P20 delivers the **CLI to an individual machine** — the *self-serve* delivery.
The web consoles are server-deployed (P19), not end-user-installed; the README is explicit that this is **"not
a desktop app."** P20 packages **only the CLI**.

## What Changes

- **New capability `release-pipeline`.** A **tag-triggered GitHub Actions** workflow (`.github/workflows/release.yml`)
  that builds the CLI on the **native runner** for each supported target (macOS / Ubuntu / Windows runners),
  invoking `release-cli.sh` — **cross-CGO is refused** because the CLI links CGO tree-sitter frontends. It
  **merges** the per-runner binaries into **one sorted `SHA256SUMS`**, **signs** it with the ed25519 release key
  from a CI secret (`SHA256SUMS.sig`), and **publishes a non-draft GitHub Release** whose assets include every
  binary, the checksum manifest + signature, the packaged installers, and the container-image reference — with
  **no human in the upload path**. The job is **idempotent/retryable**; the version is stamped **from the tag**
  into `internal/cli.ToolVersion` as the single source of truth; the pipeline **fails** on an incomplete matrix,
  an unsigned manifest on a non-dev channel, or a reproducibility regression.
- **New capability `install-channels`.** A `curl … | sh` (macOS/Linux) and PowerShell (`irm … | iex`, Windows)
  installer that **detects OS + arch**, downloads the matching Release asset, **verifies the checksum against
  `SHA256SUMS` and the signature against the pinned public key, and only then places the binary on `PATH`** —
  **failing closed** on any verification failure. Plus a **Homebrew tap**, a **Scoop** + **winget** manifest,
  `.deb`/`.rpm` packages, and a `ghcr.io` **container image** for CI/musl/Alpine — all **generated by the release
  pipeline** from the released assets, never hand-maintained. Every channel installs the requested version
  (latest by default, pinned when asked) and is uninstallable by its own idiom.
- **New capability `platform-trust`.** The macOS Gatekeeper and Windows SmartScreen posture: each OS's artifacts
  are delivered either **signed (Developer-ID + notarized / Authenticode)** or **unsigned with a documented
  one-command quarantine-clear** step surfaced in docs *and* installer output — the choice **recorded as a
  decision, not defaulted silently** — and the posture is **stated honestly** in the release notes and README
  (never claim "notarized" for a channel that isn't).
- **New capability `first-run-onboarding`.** `heros` with **no arguments** prints a **zero-config** greeting
  naming the first command; `heros init` writes a starter config with safe defaults; `heros doctor` checks local
  prerequisites (toolchain, provider-key presence, write access) and, on any gap, **names the single next
  action** — never failing silently and never demanding a prerequisite the command does not need. Local commands
  stay fully functional **offline with no account**.
- **New capability `self-update`.** `heros upgrade` fetches the latest release, **verifies checksum + signature
  exactly as a fresh install**, and replaces the binary in place — **never** executing a download before
  verification, a no-op when current, and **deferring to the package manager** when manager-installed. `heros`
  makes **no update-check network call on the hot path** of ordinary commands; any "newer version available"
  notice is **opt-out-able** and non-blocking, and the CLI sends **no telemetry**.

**No breaking changes.** `release-cli.sh`, `herossign`, the reproducible build, the published release public
key, and every existing CLI command are unchanged; P20 adds a pipeline around them, install channels that call
them, and onboarding/update subcommands beside them.

## Impact

- **Affected capabilities:** new — `release-pipeline`, `install-channels`, `platform-trust`,
  `first-run-onboarding`, `self-update`. Consumes (does not modify) the P11 `cli` and `ci-integration`
  capabilities, `release-cli.sh`, `herossign`, and the P19 deploy.
- **Affected code / systems:** `.github/workflows/release.yml` (new); `scripts/install.sh`, `scripts/install.ps1`
  (new); a packaging tree under `packaging/{homebrew,scoop,winget,nfpm}` (new); `deploy/Dockerfile.heros` (new,
  distinct from `Dockerfile.agentd`); `internal/cli/` new subcommands (`upgrade`, `doctor`, `init`, no-arg
  greeting) and a shared **verify** routine reused by installer and updater; `internal/release` (reused for
  verify); `docs/release/` install + trust runbook; README install section.
- **Dependencies:** upstream — P11 (`heros` binary, `release-cli.sh`, `herossign`, reproducible build,
  `heros-release.pub`, contract-version window), P19 (platform deploy for *linked* mode). Unblocks — self-serve
  GA (M16), a public Releases page a stranger can install from, package-manager presence, a future signed hosted
  apt/yum repo, and any future auto-update channel.
- **Explicitly out of scope (owned elsewhere):** what the CLI computes (P11); platform/server + cluster + air-
  gapped deployment and the consoles (P19); a GUI installer / desktop app (out by the product's "not a desktop
  app" framing); app-store distribution; a hosted apt/yum repo (first cut attaches packages to the Release);
  native `windows/arm64` and musl/Alpine binaries (disclosed limits, answered by the container image).
