# Install Channels — Spec Delta (P20)

Product rationale: [`../../../../docs/prd/P20-installable-packages.md`](../../../../docs/prd/P20-installable-packages.md)
§6 (FR6–FR9) and §9 (DevOps + Product lenses). Architecture: [`../../design.md`](../../design.md) Decisions 4, 5, 6.
Inherits the P11 verification contract ([`docs/release/cli-verification.md`](../../../../docs/release/cli-verification.md)):
the CLI "runs inside your CI with access to your repository, so a compromised release is a compromise of every
build it runs in."

Covers the install surfaces a real user reaches — `curl … | sh`, PowerShell, Homebrew, Scoop/winget,
`.deb`/`.rpm`, and a container image — each of which **verifies the signature before the binary is runnable**,
so the security step the threat model depends on is never silently dropped.

> Interaction-simplicity-first: the install is one command; the user never has to know what ed25519 is to be
> safe — the channel verifies **for** them.

## ADDED Requirements

### Requirement: A one-command installer SHALL verify the signature before placing the binary on PATH

A `curl … | sh` (macOS/Linux) and a PowerShell (`irm … | iex`, Windows) installer SHALL detect the OS and
architecture, download the matching Release asset together with `SHA256SUMS` and `SHA256SUMS.sig`, **verify the
checksum and then the ed25519 signature against the pinned public key**, and only then place the binary on
`PATH`.

#### Scenario: A clean install verifies and lands on PATH
- **WHEN** a user runs the one-line installer on a supported OS/arch
- **THEN** the installer downloads the matching binary, verifies its checksum against `SHA256SUMS`, and verifies
  `SHA256SUMS.sig` against the in-repo public key
- **AND** only on success does it place `heros` on the user's `PATH`, after which `heros version` prints the
  released version.

#### Scenario: OS and arch are auto-detected
- **WHEN** the installer runs
- **THEN** it selects the asset matching the host OS and architecture without the user specifying either
- **AND** an unsupported OS/arch produces a clear message naming the container-image alternative, not a wrong
  binary.

### Requirement: An installer SHALL fail closed on any verification failure

Any checksum or signature verification failure SHALL be a **hard stop** with a clear message and **no partial
install** — the installer SHALL NOT fall back to installing an unverified binary.

#### Scenario: A tampered asset is refused
- **WHEN** the downloaded binary's checksum does not match `SHA256SUMS`, or the signature does not verify
- **THEN** the installer stops with an explicit failure and installs nothing
- **AND** it does not offer or perform an "install anyway, unverified" fallback.

### Requirement: Package-manager channels SHALL be generated from the release and yield the same verified binary

A Homebrew tap formula, a Scoop manifest, a winget manifest, and `.deb`/`.rpm` packages SHALL be **generated by
the release pipeline** from the released assets and their checksums — not hand-maintained — and installing
through any of them SHALL yield the same verified binary as the one-command installer.

#### Scenario: Manifests are generated, not hand-edited
- **WHEN** a release publishes
- **THEN** the Homebrew/Scoop/winget/nfpm manifests are written by the pipeline with the tag's version and the
  emitted checksums
- **AND** no manifest carries a separately hand-edited version or checksum that can drift from the binary.

#### Scenario: Every channel installs the same binary
- **WHEN** the same version is installed via `brew`, `scoop`/`winget`, and `.deb`/`.rpm`
- **THEN** each yields a `heros` whose checksum matches the released `SHA256SUMS` line for that target.

### Requirement: A container image SHALL serve the musl/Alpine/CI case

A container image (`ghcr.io/heros-foreal/heros:<version>`, and `:latest` on GA) SHALL be published, digest-
pinned, carrying the same CLI, to serve Alpine/musl and generic-CI users for whom the glibc CGO binary does not
run.

#### Scenario: The image runs where the native binary cannot
- **WHEN** a user on Alpine/musl runs `docker run ghcr.io/heros-foreal/heros:<version> version`
- **THEN** it prints the released version
- **AND** the native musl case is documented as a disclosed limit answered by this image, not a silently missing
  target.

### Requirement: Every channel SHALL install a requested version and be uninstallable by its own idiom

Each channel SHALL install the version the user asks for (latest by default, a specific version when pinned) and
SHALL be uninstallable by the same channel's idiom; a specific prior version SHALL be installable as the
documented rollback.

#### Scenario: A pinned version installs
- **WHEN** a user requests a specific version through any channel
- **THEN** that exact version is installed and verified
- **AND** the latest is installed only when no version is pinned.

#### Scenario: Rollback is installing the prior version
- **WHEN** a user needs to roll back
- **THEN** the documented path is installing `@<previous-version>` through the same channel
- **AND** there is no in-place downgrade that bypasses verification.
